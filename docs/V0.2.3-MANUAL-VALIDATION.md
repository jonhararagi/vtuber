# V0.2.3 — Validación manual de Windows

**Estado:** pendiente de ejecución humana. Esta guía no implica aceptación de V0.2.3.

## CÓMO IDENTIFICAR EL PAQUETE AUTORIZADO

Selecciona el paquete en cada sesión a partir del HEAD que se va a validar. No uses un nombre, ID, digest, enlace de ejecución o fecha de expiración copiados de una sesión anterior como autorización permanente.

1. Abre el [PR #9](https://github.com/jonhararagi/vtuber/pull/9). Confirma que la rama de origen sea `v0.2.3/stabilization-gate` y registra el HEAD actual de esa rama mostrado por GitHub. Si la rama o el HEAD no son los esperados, detente y aclara qué revisión debe validarse.
2. Abre la pestaña **Checks** del PR o el historial de [Windows CI](https://github.com/jonhararagi/vtuber/actions/workflows/windows-ci.yml) y localiza una ejecución completada satisfactoriamente para esa rama.
3. Abre los detalles de la ejecución y comprueba que el campo **Head SHA** (el commit de la rama que disparó la ejecución) coincide exactamente, carácter por carácter, con el HEAD actual registrado en el paso 1. Si no coincide, la ejecución es anterior o corresponde a otra revisión: no la uses.
4. Confirma que la ejecución terminó con éxito y que el trabajo **build-test** completó satisfactoriamente estos pasos: **Restore solution**, **Build Release**, **Run automated tests**, **Publish self-contained Windows x64 validation package** y **Upload temporary validation artifact**. Si falta alguno, está pendiente o falló, detente.
5. Desde esa ejecución concreta, abre **Artifacts** y descarga el paquete de validación Windows x64 publicado por ella. No selecciones un artefacto de otra ejecución.
6. Registra el nombre, ID y digest del artefacto tal como aparecen en GitHub, junto con el Run ID y el HEAD de la rama. Conserva esos datos como evidencia de esta sesión de prueba.
7. Si no hay una ejecución satisfactoria para el HEAD actual, el artefacto no aparece disponible, el digest no está informado o los SHA no coinciden, detente. No uses un paquete anterior como sustituto. Registra el bloqueo y espera a que exista una ejecución satisfactoria para el HEAD actual.
8. No confundas el SHA de integración que pueda aparecer como sufijo en el nombre del artefacto con el **Head SHA** de la ejecución. Para autorizar el paquete, compara el Head SHA de la ejecución con el HEAD de la rama del PR; el sufijo del nombre no sustituye esa comprobación.

**Regla de autorización:** solo continúa si el HEAD actual de la rama y el Head SHA de la ejecución coinciden exactamente, la ejecución y todos los pasos requeridos terminaron correctamente, y el artefacto está disponible dentro de esa ejecución. Si cualquiera de esas condiciones no se cumple, marca la selección como **BLOQUEADA**.

Después de descargarlo, extrae el contenido en una carpeta nueva y escribible, por ejemplo `Documentos\\VTuberBot-V0.2.3-Test`. No copies bases de datos, configuraciones ni logs de otra instalación. Comprueba que contiene `VtuberBot.App.exe` y `BUILD-INFO.txt`. Guarda el SHA que indica `BUILD-INFO.txt` y compáralo con la información de procedencia registrada. Si no puedes reconciliarlo, marca el paso como **FALLIDO** y no continúes con ese paquete.

**Esperado:** descarga y extracción sin errores, ejecutable y BUILD-INFO presentes, y procedencia del paquete identificada y registrada.  
**Fallo:** ZIP corrupto, ejecutable ausente, artefacto no disponible o procedencia/SHA que no se puede reconciliar.

## Pruebas

Registra cada paso como **APROBADO**, **FALLIDO** o **NO EJECUTADO**. Esta tabla corresponde al paquete construido para el HEAD que se está validando; no marques como aprobada una prueba basándote en una compilación anterior. Si falla, anota el mensaje literal y el paso.

| Paso | Acción | Resultado esperado | Criterio de fallo | Resultado |
|---|---|---|---|---|
| 1 | Abrir `VtuberBot.App.exe` y comprobar el estado inicial de la ventana | La ventana abre sin cierre inesperado; el estado inicial normalmente es `RUNNING` porque la aplicación se inicializa antes de mostrar la ventana | No abre, se cierra, muestra una excepción no controlada o el estado visible no coincide con el estado real | NO EJECUTADO |
| 2 | Si el estado inicial es `RUNNING`, pulsar **Detener** | El estado cambia a `STOPPED` y la ventana sigue respondiendo. Si ya aparece `STOPPED`, registra que no fue necesario detenerla | El control no funciona, la interfaz se bloquea o el estado no cambia correctamente | NO EJECUTADO |
| 3 | Pulsar **Iniciar** | El estado cambia a `RUNNING` y la interfaz sigue respondiendo | El control no funciona, la interfaz se bloquea o el estado no cambia correctamente | NO EJECUTADO |
| 4 | Con la aplicación iniciada, ejecutar `help` | Se muestra la ayuda de comandos | Error no controlado o no aparece una respuesta de ayuda | NO EJECUTADO |
| 5 | Ejecutar `status` | La salida conserva los campos `Name`, `Version` y `State`; informa `Version: 0.2.3` y el estado actual `Running`/`RUNNING` según la representación de la interfaz | Falta algún campo, la versión no es `0.2.3`, el estado no corresponde al estado actual o aparece un error | NO EJECUTADO |
| 6 | Ejecutar `ping` | Se obtiene `pong` | Error no controlado o no se obtiene `pong` | NO EJECUTADO |
| 7 | Completar cinco ciclos adicionales de **Detener** y **Iniciar** | En cada ciclo, comprobar primero `STOPPED` tras Detener y después `RUNNING` tras Iniciar; la interfaz sigue respondiendo | Cualquier ciclo se bloquea, lanza una excepción no controlada o deja un estado incoherente | NO EJECUTADO |
| 8 | Mantener la aplicación activa durante diez minutos completos | La app permanece activa y responde; no hay cierres inesperados ni errores nuevos atribuibles a la app | Cierre, bloqueo, excepción no controlada o crecimiento de recursos claramente anormal | NO EJECUTADO |
| 9 | Cerrar la ventana y comprobar el proceso | La ventana se cierra y el proceso termina | El proceso permanece ejecutándose sin una razón esperada | NO EJECUTADO |

No se han definido umbrales numéricos de CPU o RAM para esta versión. Registra las observaciones, pero no inventes un límite de aceptación. Si la aplicación escribe logs, revisa los generados dentro de la carpeta de prueba y anota cualquier excepción relevante.

## Evidencias que deben registrarse

- Fecha, versión de Windows y SHA de origen del paquete.
- Rama, HEAD actual, Run ID, Head SHA de la ejecución, nombre e ID del artefacto y digest.
- Resultado de la comprobación de procedencia y de cada uno de los nueve pasos.
- Si la prueba de diez minutos se completó íntegramente.
- Si el proceso terminó después de cerrar la ventana.
- Incidencias y, si es posible, capturas de pantalla o extractos de log sin secretos ni datos personales.

## Qué demuestra cada tipo de verificación

- **CI:** Restore solution, Build Release, pruebas automatizadas, publicación autocontenida Windows x64 y carga del artefacto ejecutados en la ejecución seleccionada.
- **Verificación de procedencia:** rama, HEAD actual, Head SHA de la ejecución y metadatos del artefacto comparados y registrados. La metadata confirma la procedencia declarada por GitHub; no equivale a una inspección manual de cada archivo del ZIP.
- **Validación manual:** apertura e interacción real de WPF, ciclos repetidos, ejecución de diez minutos y cierre de proceso en Windows.
- **Bloqueo de aceptación:** cualquier fallo reproducible de los pasos requeridos o ausencia de evidencia para una prueba obligatoria.

V0.2.3 solo puede marcarse como aceptada cuando la lista manual esté completa, las incidencias bloqueantes estén resueltas y las evidencias estén documentadas.
